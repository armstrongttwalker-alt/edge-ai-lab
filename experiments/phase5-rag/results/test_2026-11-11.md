# Phase 5 RAG 知识库 测试结果
# Date: 2026-11-11
# Device: Radxa Orion O6N (CIX P1)
# 方案: TF-IDF 字符级向量 + SQLite 向量存储 + 余弦检索 + Phase 4 LLM 网关

## 实验说明

chromadb 1.5.9 依赖链过深（onnxruntime 100MB+、pydantic-settings、jsonschema 等），国内镜像频繁超时。
改用零依赖轻量方案：自实现 TF-IDF Embedding + SQLite 向量库 + numpy 余弦检索。
完整展示 RAG 核心原理：文档分块 → 向量化 → 存储 → 检索 → LLM 回答。

## 测试结果

| 问题 | 检索耗时 | LLM 耗时 | Top-1 检索 | 回答 |
|---|---|---|---|---|
| 这台设备的 NPU 算力是多少？ | 0.4ms | 1947ms | score=0.5001 (Zhouyi V3 30 TOPS) | **30 TOPS** ✅ |
| MobileNetV2 在 NPU 上比 CPU 快多少倍？ | 0.5ms | 1424ms | score=0.8374 (8.6倍) | **8.6** ✅ |
| Execution Provider 的名称是什么？ | 0.5ms | 1785ms | score=0.9202 (ZhouyiEP) | **ZhouyiExecutionProvider** ✅ |
| FlagOS 路线的 PP512 性能是多少？ | 0.5ms | 2016ms | score=0.6558 (589 tok/s) | **589 tok/s** ✅ |

## 性能数据

- 入库：10 篇文档，0.004s
- 检索：0.4-0.5ms（TF-IDF 向量化 + 余弦相似度）
- LLM：1.4-2.0s（含 RAG context，比纯对话稍慢因 prompt 更长）
- 准确率：4/4 全部命中正确答案

## 架构

```
用户问题
  ↓ TF-IDF 向量化（字符级 unigram+bigram, 256维）
  ↓ SQLite 存储的文档向量余弦检索 Top-3
  ↓ 拼接 context + question
  ↓ POST /v1/chat/completions → Phase 4 网关 → llama-server
  ↓ LLM 基于检索片段回答
```

## 关键发现

1. 轻量方案在边缘设备上完全可行，无重型依赖
2. 字符级 TF-IDF 对中文技术文档检索效果好（Top-1 score 0.50-0.92）
3. RAG 让 LLM 能准确回答私有文档内容（对比纯 LLM 无法知道 NPU 实测数据）
4. 整个流程端到端 < 2.5s，满足交互式问答需求
